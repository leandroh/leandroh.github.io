Install Phoenix in one command (up and running)

July 26, 2026 · 7 min read

I’ve been learning Elixir slowly, in my spare time, through pet projects. The kind of learning that lives in the gaps of a week. Which means the enemy isn’t difficulty — it’s friction. If I sit down with 40 minutes and spend 35 of them installing a language runtime, the project dies right there.

Phoenix now ships a one-liner that removes exactly that friction:

curl https://new.phoenixframework.org/myapp | sh

On my machine that went from nothing installed to a Phoenix app answering HTTP requests in 150 seconds. No Erlang, no Elixir, no Postgres beforehand.

That’s the advertised command, and it works. But it isn’t the one I ran.

Download it first

Piping a remote script straight into your shell means a server you don’t control gets to run arbitrary code as your user, and you never see what it did. You don’t have to be paranoid about the Phoenix team specifically to dislike that shape — the URL is fetched over the network every time, and “it was fine last week” isn’t a guarantee about today.

So download it, then run it:

curl -fsS -o myapp_new.sh https://new.phoenixframework.org/myapp
sh myapp_new.sh

This isn’t my invention. It’s the first thing the script’s own header comments tell you to do:

# To run locally without | sh:
#
#     $ curl -fsS -o myapp_new.sh https://new.phoenixframework.org/myapp
#     $ sh myapp_new.sh

The Phoenix folks put the safer path in the file and the convenient path on the website. Take the one in the file. It costs you one extra command.

And the reading is genuinely worth it, which is the part I didn’t expect. It’s 94 lines of sh — a two-minute read, no cleverness, no minified blob. In those two minutes you learn where the runtime gets installed, which versions you’re being handed, and the one decision the script quietly makes on your behalf that you might want to override. That’s a better deal than most installers offer.

One detail you’ll notice immediately: the URL path becomes your app name. The server templates it into the script before sending it, so curl .../blog hardcodes an app called blog. Underscores work too.

The four things it does

1. Installs Elixir and Erlang into ~/.elixir-install. Pinned versions — Elixir 1.19.0 on OTP 28.1 — fetched from official release tarballs. Not Homebrew, not asdf, not your system package manager. Its own directory, which is the detail I liked most: I already have asdf on this machine, and the two never met. Nothing to un-break later.

2. Installs the phx_new archive. Pinned to 1.8.1, via mix archive.install hex phx_new 1.8.1 --force.

3. Picks a database for you. More on this below, because it’s the decision worth knowing about.

4. Generates the app, sets it up, and starts the server — mix phx.new, then mix setup, then mix phx.server --open. That last flag opens your browser. The run ends with a working page in front of you, not with instructions.

The database choice is dumber than it looks

Here’s the whole decision:

if command -v psql >/dev/null 2>&1; then
  # default, Postgres
elif command -v mysql >/dev/null 2>&1; then
  db_option="--database mysql"
else
  db_option="--database sqlite3"
fi

It checks whether the client binary exists. Not whether a server is running, not whether you can connect, not whether there’s a database it’s allowed to touch. So if you have Postgres.app installed but not started, or a psql left over from some other project, the script confidently picks Postgres and then mix setup walks into a connection error.

I had neither psql nor mysql, so I got the SQLite branch — and for “I want to try Phoenix on a Tuesday night,” SQLite is the right answer anyway. The resulting config is refreshingly boring:

config :myapp, Myapp.Repo,
  database: Path.expand("../myapp_dev.db", __DIR__),
  pool_size: 5

No host, no user, no password, no service to start. Just a file. myapp_dev.db, in WAL mode.

What 150 seconds looks like

I timed each line. The condensed version:

[    0.3s] downloading elixir-otp-28.zip
[    0.3s] downloading otp-aarch64-apple-darwin.tar.gz
[   52.0s] unpacking otp-aarch64-apple-darwin.tar.gz
[   54.9s] checking Elixir... 1.19.0 ok
[   60.1s] installed phx_new 1.8.1
[   60.2s] Using SQLite for the Ecto adapter.
[   60.5s] * running mix deps.get
[   74.9s] * running mix deps.compile
[  144.0s] The database for Myapp.Repo has been created
[  149.7s] Running MyappWeb.Endpoint with Bandit 1.12.3 at 127.0.0.1:4000
[  150.2s] GET / — Sent 200 in 48ms

Two steps own almost all of it: unpacking the Erlang tarball (~43s) and mix deps.compile (~67s). Everything else is noise. Cost on disk: 185 MB for the runtime, 137 MB for the generated app.

What you get in 2026 is a more opinionated Phoenix than I expected — Phoenix 1.8.9, LiveView 1.1.32, Bandit rather than Cowboy as the web server, Tailwind v4 and daisyUI vendored into assets/, a tsconfig.json sitting there in case you want TypeScript, and a git repo already initialised (though with zero commits — the first one is yours to make).

The generator doesn’t know it’s being driven

My favourite moment in the log. At 141.7s, mix phx.new prints this:

We are almost there! The following steps are missing:

    $ cd myapp

Then configure your database in config/dev.exs and run:

    $ mix ecto.create

Start your Phoenix app with:

    $ mix phx.server

And then the script immediately does all three. phx.new is just being itself — it has no idea a wrapper is about to finish its homework. But if you’re new, you now have a to-do list on screen that is already done, and no way to know that. Ignore it.

The one thing that actually bit me

The install is real, and it’s invisible.

$ zsh -lic 'command -v elixir'
NOT FOUND in fresh shell

The script exports the PATH inside its own process, which is enough for the app to get built and the server to start — and that’s where it ends. Nothing is written to your .zshrc. Open a new terminal and elixir doesn’t exist.

To be fair, the installer tells you. At second 55 of a 150-second run:

Run this (or add to your ~/.bashrc or similar file):

    export PATH=$HOME/.elixir-install/installs/otp/28.1/bin:$PATH
    export PATH=$HOME/.elixir-install/installs/elixir/1.19.0-otp-28/bin:$PATH

So it’s not undocumented. It’s buried. Ninety-five more seconds of dependency resolution scroll past after that, and then your browser opens with a working Phoenix page, and you are absolutely not scrolling back up. Add those two lines to your shell profile — it’s the only manual step the whole thing really needs.

When to skip it

This is a great front door and a bad long-term plan. If you already manage runtimes with asdf or mise, install Elixir the way you install everything else, then mix phx.new myapp and stay in control of your own versions. Same if you specifically need Postgres, or you’re on an OS the script doesn’t cover — mix phx.new is the real tool here, and the installer is a thin, friendly shell around it.

But for the actual problem I had — wanting to write some Elixir before losing interest — this is exactly right. The friction is the thing that kills spare-time projects, and someone went and deleted it.
